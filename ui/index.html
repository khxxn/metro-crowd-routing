혼잡도 길찾기5분 더 걸려도 덜 붐비는 길은?

서울 지하철에서 가장 빠른 길과 덜 붐비는 길을 알고리즘별로 비교합니다. 점수는 혼잡과 환승 부담을 반영한 시간(분)이고, 낮을수록 덜 붐비고 편한 길입니다. 실제 시간은 열차를 타고 걷고 기다리는 실제 소요입니다.

1어디서 어디로 가나요?

출발역
도착역

사용한 것 브라우저 기본 선택 목록(<select>)과 검색 입력, 서버 API /api/lines(호선별 역 순서)·/api/stations(역 이름과 지나는 호선). 역 데이터는 data/station_nodes.csv, 서울 1~9호선뿐입니다.

만든 방식 호선을 고르면 그 호선의 역을 노선 순서대로 보여주고, "전체 호선"은 모든 역을 가나다순으로 보여줍니다. 검색칸은 현재 목록에서 이름에 글자가 들어간 역만 남깁니다. 환승역처럼 같은 이름의 노드가 여러 개이면 모두 출발점(도착점)으로 씁니다.

2언제, 어떤 조건으로 가나요?

사용한 것 입력값은 /api/route로 서버에 보내고, 서버가 graph.py의 Config로 바꿔 계산합니다. 혼잡도는 data/ride_congestion_filled.csv(간선·요일·시간대별 %)입니다.

만든 방식 하루를 05:30부터 30분 간격 39칸으로 나눠 그 칸의 혼잡도를 찾습니다. 탑승 구간 점수 = 탑승 시간 × (1 + ALPHA × max(혼잡도 − 33.75, 0)), 환승 점수는 팀 CSV의 값(걷기+대기의 2.204배)입니다. 허용 시간 T = 최단 실제 시간 + 허용 여유이고, T 안에서 점수가 가장 낮은 길을 찾는 것이 LARAC·정답 기준입니다.

3어떤 알고리즘으로 비교할까요?

사용한 것 파이썬 표준 라이브러리 heapq(우선순위 큐)로 직접 구현한 알고리즘들입니다(algorithms/ 폴더). 라이브러리의 길찾기 함수는 쓰지 않았습니다.

만든 방식 같은 질의를 고른 알고리즘마다 실행해서 결과를 나란히 비교합니다. A*는 도착역에서 거꾸로 계산한 하한을 길잡이로 써서 점수가 가장 낮은 길을 찾고, LARAC은 "점수 + λ × 시간" 가중치를 바꿔 가며 허용 시간 안의 답을 찾습니다. 정답 기준은 (시간, 점수) 후보를 모두 추려서 허용 시간 안의 정확한 답을 냅니다. 이 화면에는 Dijkstra를 따로 보여주지 않습니다(A*·LARAC·정답 기준이 내부에서 최단 시간·하한을 계산할 때만 씁니다).

출발·도착 쌍별 결과

사용한 것 서버 /api/line_experiment가 experiments/run.py의 sample_line_ods(쌍 고르기)와 _timed(실행 시간 3회 중앙값)로 A*·LARAC·정답 기준을 같은 질의에 돌립니다. 같은 설정이면 같은 쌍(시드 42)이 나오고, 한 번 돌린 결과는 서버가 기억합니다.

만든 방식 선택한 호선에 출발·도착역이 모두 있고, 점수 최소 경로의 탑승 구간 80% 이상이 그 호선인 쌍만 뽑습니다. "전체"는 호선 제한 없이 무작위로 뽑습니다. 오차 = (알고리즘 점수 − 정답 기준 점수) ÷ 정답 기준 점수 × 100이고, 허용 시간 안에 도착한 결과만 계산합니다. 한 호선 안에서만 움직이는 쌍은 갈아탈 대안이 거의 없어서 알고리즘들이 같은 경로를 내는 경우가 많습니다. 그래서 오차가 0%로 나오는 것은 버그가 아니라 정상입니다. 실행 시간이 가장 긴 알고리즘을 "가장 비효율적"으로 표시합니다. 유전 알고리즘은 아직 연결되지 않아 빠졌습니다.
